# 现有效果保护下的低代码改造实施建议

## 1. 核心结论

当前项目不适合直接改造成完整的通用低代码平台，更适合做成：

**后台低代码资料采集，前台固定模板展示。**

也就是说，低代码能力主要服务后台：

- 让管理员可以快速配置资料模板。
- 让老师可以按模板填写资料。
- 让系统自动把填写内容转换成现有展示数据。
- 让前台继续使用现在已经确定的学校门户、系部门户、专题页、卡片轮播和抽屉详情样式。

这条路线最稳，因为它能满足“低代码快速开发业务功能”的要求，又不会推翻现在已经调好的前端效果。

## 2. 为什么不能大改

现在项目前端已经有比较明确的展示方向：

- 学校门户页。
- 系部门户页。
- 创新育人专题页。
- 板块卡片。
- 无缝循环滚动。
- 详情抽屉。
- 图片原比例缩放和轮播。
- `/display?project=...&code=...` 扫码详情页。

这些展示效果已经是项目资产。如果为了追求“低代码”去做页面自由拖拽、自由布局、自由样式，很容易出现三个问题：

- 前台视觉失控，不同老师做出来的页面风格不统一。
- 数据结构混乱，后期维护和审核会越来越难。
- 工程量变大，容易影响现有页面稳定性。

所以低代码改造应该服务“资料怎么录入”，而不是服务“页面怎么随便搭”。

## 3. 产品定位

建议后台模块名称不要叫“低代码平台”，而叫：

**资料采集模板**

这个名字更符合学校使用场景。老师和管理员真正需要的是“按规范上传资料”，不是学习一个复杂的页面搭建系统。

推荐后台形成这样的逻辑：

```text
选择门户
  -> 选择专题 / 系部
  -> 选择板块
  -> 选择资料模板
  -> 填写内容
  -> 上传图片 / 视频
  -> 提交审核
  -> 前台自动展示
```

## 4. 改造难度评估

整体难度：**中等，可控。**

不是简单加几个字段，但也不需要推翻项目。真正需要谨慎的是数据库、后台表单、审核流程和已有前台兼容。

| 模块 | 难度 | 风险 | 建议 |
| --- | --- | --- | --- |
| 后台资料模板 | 中 | 中 | 先做固定控件和字段配置 |
| 动态表单渲染 | 中 | 中 | 只在后台做，不影响前台 |
| 数据库新增低代码表 | 中 | 中 | 新增表，不改旧表核心逻辑 |
| 映射到 content_items | 中 | 高 | 必须复用现有展示数据结构 |
| 前台展示适配 | 低 | 中 | 原则上不改样式，只读新数据 |
| 审核发布流程 | 中 | 中 | 沿用现有审核逻辑 |
| 页面自由拖拽 | 高 | 高 | 第一阶段不做 |

推荐判断：

- 做“资料采集模板”：适合现在推进。
- 做“完整低代码平台”：暂时不建议，风险偏高。

## 5. 改造边界

### 5.1 第一阶段要做

- 固定创新育人专题板块。
- 固定资料类型。
- 后台支持模板化填写资料。
- 管理员可以配置字段。
- 老师只填写，不设计页面。
- 表单提交后生成 `content_items`。
- 图片和视频继续进入现有素材体系。
- 提交后进入现有审核发布流程。
- 前台继续按现有样式展示。

### 5.2 第一阶段不做

- 不做前台页面自由拖拽。
- 不做万能业务建表。
- 不做复杂流程设计器。
- 不做自定义 CSS。
- 不允许老师修改前台布局。
- 不把现有展示页面推倒重来。

## 6. 固定业务模板

创新育人专题建议固定为 11 个板块：

| 顺序 | 板块 | key | 说明 |
| ---: | --- | --- | --- |
| 1 | 专题概况 | overview | 专题背景、建设目标、整体介绍 |
| 2 | 专业群布局 | majors | 专业设置、课程体系、就业方向 |
| 3 | 实训场景 | training | 实训基地、设备、教学场景 |
| 4 | 产教协同 | cooperation | 校企合作、订单班、共同体 |
| 5 | 名师名匠 | masters | 教学名师、技能大师、教师团队 |
| 6 | 优秀校友 | alumni | 校友人物、就业成果、成长故事 |
| 7 | 优秀学生 | students | 学生人物、竞赛经历、成长案例 |
| 8 | 专题成果 | achievements | 教学成果、项目成果、建设成果 |
| 9 | 技能大赛 | competitions | 赛事、获奖、承办活动 |
| 10 | 荣誉资质 | honors | 证书、奖项、资质认定 |
| 11 | 视频资源 | media | 宣传片、访谈、纪实视频 |

资料类型建议固定为 7 类：

| 类型 | key | 适合内容 |
| --- | --- | --- |
| 普通图文 | article | 概况、介绍、说明类内容 |
| 人物 | person | 教师、校友、学生 |
| 活动 | activity | 比赛、合作、培训、交流 |
| 荣誉 | honor | 证书、奖项、认定 |
| 成果 | achievement | 项目成果、建设成果、案例 |
| 场景 | scene | 实训室、基地、教学空间 |
| 视频 | video | 视频资源和宣传片 |

## 7. 后台角色设计

### 7.1 管理员

管理员负责模板和审核。

管理员可以做：

- 创建资料采集模板。
- 从内置模板复制。
- 修改字段名称、字段类型、必填状态。
- 设置字段映射。
- 启用或停用模板。
- 查看模板版本。
- 审核老师提交的资料。

管理员不应该直接在前台拖动页面布局。

### 7.2 老师

老师负责填写资料。

老师可以做：

- 选择自己负责的门户。
- 选择对应板块。
- 选择资料模板。
- 填写文字内容。
- 上传图片、视频、附件。
- 保存草稿。
- 提交审核。

老师不需要理解 `content_items`、字段映射、页面布局这些技术概念。

## 8. 数据流设计

推荐保持现有 `content_items` 作为前台展示主数据源。

低代码表单只作为后台采集层。

```text
lowcode_forms
  -> lowcode_form_versions
  -> lowcode_records
  -> content_items
  -> 前台门户 / 专题页 / 抽屉详情
```

这样前台不需要知道资料是普通编辑器录入的，还是低代码表单录入的。

## 9. 数据库建议

新增低代码相关表，不破坏旧表。

### 9.1 lowcode_forms

保存模板基础信息。

建议字段：

- `id`
- `name`
- `code`
- `description`
- `portal_type`
- `target_module_key`
- `target_content_type`
- `enabled`
- `created_by`
- `created_at`
- `updated_at`

### 9.2 lowcode_form_versions

保存模板字段版本。

建议字段：

- `id`
- `form_id`
- `version_no`
- `schema_json`
- `created_by`
- `created_at`

### 9.3 lowcode_records

保存老师填写的原始记录。

建议字段：

- `id`
- `form_id`
- `form_version_id`
- `project_id`
- `content_item_id`
- `status`
- `data_json`
- `submitted_by`
- `submitted_at`
- `reviewed_by`
- `reviewed_at`
- `review_note`

### 9.4 lowcode_record_assets

保存低代码记录和素材之间的关系。

建议字段：

- `id`
- `record_id`
- `asset_id`
- `role`
- `caption`
- `sort_order`
- `created_at`

## 10. 字段设计建议

第一阶段字段控件不要太多，建议支持：

- 单行文本。
- 多行文本。
- 富文本。
- 数字。
- 日期。
- 下拉选择。
- 单选。
- 多选。
- 图片上传。
- 视频上传或视频地址。
- 文件上传。
- 开关。

每个字段建议包含：

- 字段名称。
- 字段编码。
- 字段类型。
- 是否必填。
- 占位提示。
- 默认值。
- 字段分组。
- 排序。
- 映射目标。

字段分组很重要。它可以让老师填写资料时不拥挤，例如：

```text
基础信息
  标题、副标题、摘要、所属板块

详情内容
  正文、人物介绍、活动说明、成果说明

媒体素材
  封面图、图集、视频、附件

展示设置
  排序、是否重点展示、是否启用
```

## 11. 前台展示策略

前台原则：**只吃结构化数据，不吃低代码配置。**

前台继续根据 `content_type` 自动选择展示方式：

| content_type | 展示逻辑 |
| --- | --- |
| article | 标题、摘要、正文、图片轮播 |
| person | 人物图、身份信息、简介、主要事迹 |
| activity | 活动时间地点、正文段落、现场图片 |
| honor | 证书图片、荣誉名称、年份、级别 |
| achievement | 成果摘要、关键指标、成果说明 |
| scene | 场景图片、功能定位、设备条件 |
| video | 视频封面、播放器、视频简介 |

低代码字段只影响数据如何录入，不影响页面如何排版。

## 12. 分阶段实施路线

### 阶段一：稳定现有展示

目标：

- 不动前台核心样式。
- 明确学校门户、系部门户、专题门户的展示边界。
- 确认 11 个专题板块和 7 类资料类型。

交付：

- 板块固定。
- 类型固定。
- 前台兼容现有数据。

### 阶段二：后台资料采集模板

目标：

- 管理员可以配置模板。
- 老师可以按模板填写。

交付：

- `lowcode_forms`。
- `lowcode_form_versions`。
- 动态表单渲染。
- 模板启用 / 停用。
- 模板复制。

### 阶段三：表单记录映射展示资料

目标：

- 低代码填写记录自动生成 `content_items`。

交付：

- `lowcode_records`。
- `lowcode_record_assets`。
- 字段映射。
- 图片和视频角色映射。
- 审核流程接入。

### 阶段四：后台体验优化

目标：

- 降低老师录入压力。
- 降低管理员维护成本。

交付：

- 字段分组。
- 图片批量上传。
- 上传预览。
- 表单提交预览。
- 模板版本记录。
- 记录状态同步。

### 阶段五：扩展业务表单

目标：

- 在资料采集稳定后，再扩展到其他业务。

可选方向：

- 活动报名。
- 成果申报。
- 校企合作项目登记。
- 实训室使用登记。
- 荣誉资质申报。

这一阶段再考虑更通用的低代码能力。

## 13. 风险控制清单

开发时建议坚持以下规则：

- 不删除旧数据。
- 不删除现有 `pages` 兼容逻辑。
- 不改前台核心视觉布局。
- 不让老师配置页面样式。
- 不让字段配置直接控制 CSS。
- 数据库改造只新增表或兼容字段。
- 大素材继续留在 `uploads/`，不要提交仓库。
- 每次数据库改造前备份 `expo.db`。
- 每次提交 GitHub 前同步 `database/expo-latest.db`。
- 每次改造后跑基础检查。

## 14. 最小可行版本

最小版本建议只做：

- 后台新增“资料采集模板”入口。
- 内置 11 个专题模板。
- 支持管理员调整字段。
- 支持老师填写模板。
- 提交后生成 `content_items`。
- 继续使用现有审核。
- 前台展示完全不大改。

暂时不做：

- 页面拖拽。
- 自定义流程。
- 自定义数据库。
- 自定义前台布局。
- 自定义主题样式。

## 15. 最终建议

项目下一步应该围绕“稳”来做：

**保留现在的前台展示效果，把后台资料录入变得更规范、更低代码、更容易维护。**

这样既能让系统具备低代码快速配置业务表单的能力，也能保护已经做好的学校门户、系部门户、创新育人专题和抽屉详情页效果。

推荐实施路线：

```text
先固定模板
  -> 再做动态表单
  -> 再映射 content_items
  -> 再优化后台体验
  -> 最后扩展更多业务
```

这是一条比较稳的路线，工程量可控，也不容易把项目改乱。
