# 后台易维护与可视化改造方案

## 1. 背景与目标

当前后台已经覆盖学校门户、系部门户、专题门户、板块资料、结构化资料、资料采集模板、素材库、审核、发布、报表、账号等完整能力，但维护入口过于集中，很多技术模型直接暴露给使用者，导致校方反馈“没有维护欲望”。

本次改造目标不是删功能，也不是单纯美化界面，而是把现有能力重新组织成校方能理解、愿意使用的工作流：

```text
选门户
  -> 看栏目缺什么
  -> 像 Word 一样编辑内容
  -> 实时看质量检查和前台预览
  -> 提交审核
  -> 发布到门户和扫码大屏
```

核心原则：

- 保留现有数据表、审核、发布和前台展示能力。
- 降低维护者理解成本，不再要求用户理解 `pages`、`content_items`、`lowcode`、`module_key` 等技术概念。
- 把高频维护行为集中到“内容工作台”和“Word 式编辑器”。
- 把治理、报表、发布检查等能力移到更清晰的管理区。
- 深度贯彻可视化：门户完整度、栏目状态、质量检查、前台预览、发布影响都要直观看见。

## 2. 当前后台维护对象

现有后台实际维护的对象包括：

| 对象 | 当前数据/代码 | 说明 |
| --- | --- | --- |
| 账号与权限 | `users`、`admin_sessions` | 管理员、系部管理员、老师账号、启用状态、密码 |
| 门户对象 | `projects` | 学校门户、系部门户、专题门户，含负责人、路由、主题色、默认图、质量规则 |
| 标准栏目 | `standardModules`、`topicModules`、`moduleSets` | 不同门户类型的栏目定义，如基本情况、专业设置、专题概况、名师名匠 |
| 旧版展示页 | `pages` | 兼容扫码大屏和历史资料，正文为 HTML |
| 展示页版本 | `page_versions` | 旧版资料审核、历史、差异 |
| 结构化资料 | `content_items` | 未来应作为主要维护模型，含栏目、内容类型、正文 JSON、扩展字段 |
| 结构化素材 | `content_item_assets` | 结构化资料绑定的图片、视频、附件、跳转按钮 |
| 结构化版本 | `content_item_versions` | 结构化资料审核、历史、差异 |
| 资料采集模板 | `lowcode_forms`、`lowcode_form_versions` | 管理员配置老师填写表单和字段映射 |
| 填报记录 | `lowcode_records`、`lowcode_record_assets` | 老师按模板提交的原始资料，可生成结构化资料 |
| 素材库 | `assets` | 图片、视频、附件统一上传和复用 |
| 发布范围 | `deployed_pages`、`projects.deployed`、`projects.content_deployed` | 欢迎页发布、扫码大屏内容发布 |
| 扫码记录 | `scans` | 扫码内容、命中项目、结果 |
| 操作日志 | `admin_logs` | 后台关键操作记录 |

当前核心问题是：这些对象都很重要，但大量内容被集中暴露在 `pagesView` 一个页面中，用户无法区分“内容维护、模板配置、旧版兼容、报表治理、审核发布”之间的边界。

## 3. 当前主要痛点

### 3.1 技术模型直接暴露

当前页面中有：

- 板块资料
- 结构化资料
- 兼容展示页
- 旧版富文本
- 资料采集模板
- 模板提交记录
- 低代码模板配置

这些能力都需要保留，但对校方来说概念过多。用户真正关心的是：

- 我负责哪个门户？
- 这个门户缺哪些栏目？
- 我要补哪篇内容？
- 内容是否合格？
- 前台效果是什么？
- 是否已审核和发布？

### 3.2 高频维护入口太深、太乱

当前“板块资料”页面同时承担：

- 选门户
- 看栏目覆盖
- 看质量检查
- 管资料采集模板
- 看填报统计
- 看模板提交记录
- 管结构化资料
- 管旧版展示页
- 打开低代码填报表单
- 打开模板配置表单
- 打开结构化资料表单
- 打开旧版富文本表单

这会导致维护者不知道从哪里开始。

### 3.3 富文本编辑体验不足

当前旧版富文本使用 `contenteditable + document.execCommand`，虽然能编辑，但离“像 Word 一样直观维护”还有差距：

- 粘贴 Word 内容不可控。
- 图片、视频、附件不是内容块的一部分。
- 无法稳定保存为结构化 JSON。
- 预览和质量检查不够贴近编辑过程。

### 3.4 发布逻辑与内容维护割裂

系统中存在两类发布：

- 欢迎页发布：影响 `/display` 默认欢迎页。
- 扫码大屏资料发布：影响扫码能打开哪些内容。

同时门户页本身又会读取已审核启用资料。普通维护人员不应该被迫理解这些细节，应在发布中心以“影响范围”和“发布检查”的形式表达。

## 4. 新后台信息架构

建议左侧一级菜单改为 7 个：

```text
工作台
门户管理
内容工作台
素材中心
审核发布
数据与报表
系统设置
```

### 4.1 工作台

用于快速判断当前系统状态。

展示内容：

- 当前欢迎页项目。
- 当前扫码大屏发布项目。
- 门户完整度排行。
- 待审核数量。
- 缺失栏目数量。
- 被驳回内容。
- 最近更新。
- 扫码通道状态。

主要动作：

- 继续维护某个门户。
- 处理待审核。
- 查看发布检查。
- 导出缺项清单。

### 4.2 门户管理

管理“有哪些门户”和“门户结构是什么”。

子区域：

```text
学校门户
系部门户
专题门户
门户结构
栏目模板
质量规则
```

推荐布局：

```text
左侧：门户树
右侧：门户详情
```

门户详情包含：

- 基础信息：名称、类型、路由、负责人、主题色、默认图片。
- 门户首页：标题、小标题、简介、封面。
- 栏目结构：栏目是否启用、排序、显示名称。
- 质量规则：最少正文字数、是否要求摘要、是否要求素材、栏目特例。
- 发布状态：前台路径、最近发布时间、预览入口。

### 4.3 内容工作台

这是校方日常最高频入口。

用户进入后：

```text
选择门户
  -> 查看栏目看板
  -> 点击栏目
  -> 查看该栏目内容列表
  -> 新建或编辑内容
```

栏目看板状态建议：

```text
未开始
草稿
待完善
待审核
已驳回
已发布
需重新发布
```

栏目卡片显示：

- 栏目名称。
- 当前状态。
- 已有内容数量。
- 可发布内容数量。
- 缺少项：摘要、正文、图片、视频、附件等。
- 负责人。
- 最后更新时间。
- 操作：编辑、预览、提交审核。

### 4.4 Word 式编辑器

具体内容编辑页采用三栏布局：

```text
左侧：内容目录 / 栏目列表
中间：Word 式正文编辑器
右侧：属性 / 素材 / 质量检查 / 前台预览 / 历史
```

编辑器应支持：

- 标题、正文、加粗、斜体。
- 无序列表、有序列表。
- 表格。
- 图片、图集。
- 视频。
- 附件。
- 引用。
- 分割线。
- 撤销、重做。
- 拖拽上传。
- 粘贴 Word 内容并清理格式。

推荐技术路线：

```text
Tiptap / ProseMirror
```

原因：

- 编辑体验接近 Word。
- 原生适合保存 JSON。
- 扩展图片、视频、附件、表格更稳。
- 比单纯 HTML 更适合长期维护和前台渲染。

保存格式建议进入 `content_items.body_json`：

```json
{
  "type": "doc",
  "content": [
    {
      "type": "heading",
      "attrs": { "level": 2 },
      "content": [{ "type": "text", "text": "专业设置" }]
    },
    {
      "type": "paragraph",
      "content": [{ "type": "text", "text": "这里是正文内容" }]
    },
    {
      "type": "image",
      "attrs": {
        "src": "/uploads/example.jpg",
        "caption": "实训现场"
      }
    }
  ]
}
```

### 4.5 素材中心

集中维护：

- 图片。
- 视频。
- PDF。
- Word。
- Excel。
- PPT。
- 压缩包。

能力：

- 上传。
- 预览。
- 复制地址。
- 绑定到当前内容。
- 按门户、上传人、类型筛选。
- 素材归档导出。

编辑器中选择素材时，应打开素材选择器，不应强制用户离开编辑流程。

### 4.6 审核发布

用于管理员集中处理：

- 门户配置审核。
- 内容审核。
- 删除申请。
- 版本历史。
- 发布欢迎页。
- 发布扫码大屏资料。

审核列表建议按门户聚合：

```text
财政经济系
  专业设置：待审核
  实训基地：已驳回

财经商贸
  名师名匠：待审核
```

发布前必须显示检查清单：

- 哪些栏目可发布。
- 哪些栏目缺失。
- 哪些内容待审核。
- 哪些内容被驳回。
- 哪些内容会进入扫码大屏。
- 当前发布会影响哪个路径。

### 4.7 数据与报表

把现在混在内容页里的治理能力移到报表区：

- 门户完整度。
- 栏目覆盖率。
- 内容质量清单。
- 素材归档。
- 填报统计。
- 催交提醒。
- CSV 导出。

这些很重要，但不是日常编辑主路径。

### 4.8 系统设置

放低频管理功能：

- 账号管理。
- 角色权限。
- 操作日志。
- 扫码记录。
- 运行状态。
- 上线配置。

## 5. 数据模型改造原则

### 5.1 不推翻现有模型

现有表保留：

- `projects`
- `pages`
- `page_versions`
- `content_items`
- `content_item_assets`
- `content_item_versions`
- `lowcode_forms`
- `lowcode_records`
- `assets`
- `deployed_pages`

### 5.2 明确主从关系

未来维护主数据：

```text
content_items = 主内容数据
```

兼容展示层：

```text
pages = 扫码大屏和旧展示兼容层
```

用户不直接感知 `pages`，除非进入高级信息。

保存或审核通过 `content_items` 后，由后端同步生成或更新对应 `pages`：

```text
content_items
  -> render/sync
  -> pages
  -> /display?project=...&code=...
```

### 5.3 资料采集模板重新命名

不要对校方显示“低代码”。

后台显示：

```text
资料采集模板
资料填报记录
```

技术层仍可使用：

```text
lowcode_forms
lowcode_records
```

管理员配置模板，老师填写模板，系统生成结构化资料。

## 6. 可视化设计要点

### 6.1 门户完整度

用进度条、状态色和缺项标签展示：

```text
财政经济系：3/8 已发布，2 个待审核，3 个未开始
财经商贸：9/11 已发布，1 个缺图片，1 个待审核
```

### 6.2 栏目看板

用看板替代表格优先级：

```text
未开始 | 待完善 | 待审核 | 已发布
```

维护人员按状态推进，而不是在大表里搜索。

### 6.3 编辑器右侧质量检查

实时显示：

```text
标题：已完成
摘要：已完成
正文：860 字
封面图：待补
标准栏目：已匹配
视频：非必填
附件：0
```

质量检查结果要直接告诉用户下一步动作，而不是只显示错误。

### 6.4 前台预览

编辑时右侧提供：

- 卡片预览。
- 门户栏目预览。
- 扫码详情页预览。

必要时打开完整前台预览。

### 6.5 发布影响可视化

发布前显示：

```text
本次发布影响：
- /display 欢迎页
- /display 扫码大屏资料
- 已选择 4 条可扫码内容
- 仍有 2 个栏目未发布
```

## 7. 推荐实施阶段

### 阶段一：信息架构重排

目标：不改数据库，不改核心接口，先把后台入口重组。

内容：

- 左侧菜单改为 7 类。
- `pagesView` 拆分为内容工作台、报表区、模板区、高级兼容区。
- “低代码”改名为“资料采集模板”。
- “兼容展示页”默认收起到高级区域。
- 工作台突出待办、缺项、发布状态。

收益：

- 风险最低。
- 用户立刻感觉清晰。
- 不影响现有前台。

### 阶段二：内容工作台

目标：建立“门户树 + 栏目看板 + 内容列表”的主流程。

内容：

- 左侧门户树。
- 中间栏目看板。
- 右侧门户状态和建议动作。
- 点击栏目进入内容列表。
- 内容列表聚合 `content_items` 和兼容 `pages` 状态。

收益：

- 维护人员知道每个门户缺什么。
- 内容维护从表格查找变成任务推进。

### 阶段三：Word 式编辑器

目标：替换分散表单和旧富文本体验。

内容：

- 引入 Tiptap/ProseMirror。
- 正文保存为 JSON。
- 支持图片、视频、附件内容块。
- 支持 Word 粘贴清理。
- 右侧实时质量检查。
- 右侧前台预览。
- 保存或审核通过后自动同步 `pages`。

收益：

- 校方获得接近 Word 的维护体验。
- 数据仍是结构化的，可控、可审核、可渲染。

### 阶段四：审核发布可视化

目标：降低管理员发布风险。

内容：

- 审核按门户和栏目聚合。
- 版本差异可视化。
- 发布前检查清单。
- 区分“门户实时展示”和“扫码大屏发布范围”。
- 支持导出缺项和发布报告。

收益：

- 管理员知道发布会影响什么。
- 减少现场误发布和漏发布。

## 8. 推荐最终交互流程

### 8.1 老师或系部维护人员

```text
打开后台
  -> 工作台看到待办
  -> 点击负责的门户
  -> 看到栏目看板
  -> 点击待完善栏目
  -> 进入 Word 式编辑器
  -> 粘贴 Word 内容
  -> 上传或选择图片
  -> 右侧质量检查变绿
  -> 预览前台效果
  -> 保存草稿或提交审核
```

### 8.2 管理员

```text
打开审核发布
  -> 按门户查看待审核内容
  -> 查看差异和前台预览
  -> 通过或驳回
  -> 进入发布检查
  -> 发布欢迎页或扫码大屏资料
  -> 导出发布报告
```

### 8.3 内容治理人员

```text
打开数据与报表
  -> 查看门户完整度
  -> 查看缺失栏目
  -> 查看素材归档
  -> 查看填报统计
  -> 导出催交清单
```

## 9. 页面原型方向

前面已做过三类 HTML 感受稿：

1. 企业后台经典版：适合门户列表、账号、审核、日志等管理页面。
2. 门户树工作台版：适合门户管理和内容工作台。
3. Word 式内容编辑器版：适合最终内容编辑体验。

建议最终组合：

```text
门户管理：门户树工作台版
内容工作台：门户树 + 栏目看板
具体编辑：Word 式内容编辑器
审核发布：企业后台经典版 + 发布检查清单
```

## 10. 落地优先级

优先级从高到低：

1. 重新设计菜单和页面分层。
2. 内容工作台栏目看板。
3. 结构化资料作为主维护入口。
4. 旧版兼容页收进高级区。
5. Tiptap Word 式编辑器。
6. 编辑器右侧质量检查和前台预览。
7. 审核发布聚合与发布检查。
8. 报表导出和催交清单。

## 11. 关键风险与注意事项

### 11.1 不要删除 `pages`

当前扫码大屏、历史数据和发布范围仍依赖 `pages`。应将它降级为兼容层，而不是删除。

### 11.2 不要让普通用户理解低代码

`lowcode_forms` 和 `lowcode_records` 保留，但前台命名必须是“资料采集模板”和“填报记录”。

### 11.3 不要做完全自由页面搭建器

自由拖拽页面搭建器看似灵活，但会破坏大屏展示稳定性，维护成本高。应采用“Word 式内容编辑 + 结构化块 + 固定前台模板”的路线。

### 11.4 不要把报表继续塞进内容编辑页

质量检查、填报统计、素材归档、缺项导出很重要，但属于治理能力，应放在“数据与报表”中，只在编辑器右侧显示当前内容相关检查。

### 11.5 发布动作必须可解释

发布前必须明确：

- 发布到哪里。
- 会影响哪个页面。
- 哪些内容会进入扫码大屏。
- 哪些栏目还缺内容。
- 是否存在待审核或被驳回内容。

## 12. 建议下一步

下一步可以开始阶段一：

1. 修改后台菜单结构。
2. 将 `pagesView` 拆成更清晰的内容工作台雏形。
3. 新增门户树和栏目看板视图。
4. 把低代码相关文案改为资料采集模板。
5. 把兼容展示页默认折叠。
6. 保留原功能入口，避免影响现有使用。
