# 低代码资料采集与后台改造产品说明

## 1. 项目判断

当前项目已经形成了比较成熟的前端展示效果，包括欢迎页、学校门户页、系部门户页、创新育人专题、卡片展示、无缝循环滚动、资料抽屉、图片轮播和扫码详情页。

因此，本阶段不建议把系统改造成完整的通用低代码平台，也不建议让老师或普通管理员自由拖拽页面、自由调整前端样式。

更稳妥的方向是：

```text
前台保持统一展示效果
后台增加低代码资料采集能力
资料按模板填写
系统自动生成展示数据
审核后进入现有门户和专题页面
```

一句话概括：

> 低代码负责让资料录入更快、更规范；前台负责用统一审美把资料展示出来。

## 2. 改造目标

本次改造的目标不是重做一个新系统，而是在现有项目基础上补齐后台资料管理能力。

核心目标如下：

- 老师可以按模板填写资料，不需要理解前端页面结构。
- 管理员可以配置资料模板，不需要每次找开发人员改表单。
- 系统可以把填报内容自动转换成现有展示数据。
- 前端继续使用现有学校门户、系部门户、专题页和抽屉详情样式。
- 图片、视频、附件可以统一上传、统一归档、统一审核。
- 后台能看出每个专题、每个板块、每个系部资料是否完整。
- 后续新增业务资料时，可以通过配置模板快速实现。

## 3. 产品定位

后台模块建议命名为：

**资料采集模板**

不建议在界面上直接叫“低代码平台”。“低代码平台”对学校用户来说概念偏技术化，容易让人误以为可以随意搭建页面。实际业务里，老师和管理员更关心的是：

- 这个资料应该填什么。
- 哪些内容必须填。
- 图片、视频、附件应该怎么上传。
- 提交后谁审核。
- 审核后在哪个页面展示。

所以后台应当用更业务化的语言组织功能。

## 4. 后台信息架构

建议后台逐步整理为以下模块：

```text
首页概览
  -> 数据完整度
  -> 待审核资料
  -> 最近更新

门户管理
  -> 学校门户
  -> 系部门户
  -> 创新育人专题

资料采集模板
  -> 模板列表
  -> 新建模板
  -> 复制模板
  -> 版本管理
  -> 启用 / 停用

资料填报
  -> 按模板填写
  -> 保存草稿
  -> 提交审核
  -> 退回修改

资料审核
  -> 待审核
  -> 已通过
  -> 已退回
  -> 已发布

素材管理
  -> 图片
  -> 视频
  -> 附件
  -> 素材归档

质量检查
  -> 专题完整度
  -> 板块覆盖情况
  -> 图片缺失检查
  -> 字数和格式检查
```

这套结构的重点是让后台从“堆功能”变成“按资料生命周期管理”。

## 5. 推荐业务流程

### 5.1 管理员配置模板

```text
选择适用范围
  -> 选择专题 / 系部 / 板块
  -> 选择资料类型
  -> 配置字段
  -> 设置必填和校验
  -> 保存模板版本
  -> 启用模板
```

管理员负责定义“什么资料应该怎么填”，而不是设计前台页面。

### 5.2 老师填写资料

```text
选择资料模板
  -> 填写文字内容
  -> 上传图片 / 视频 / 附件
  -> 保存草稿
  -> 预览填报内容
  -> 提交审核
```

老师侧界面应该尽量简单，避免出现复杂配置项。

### 5.3 审核发布

```text
老师提交
  -> 管理员审核
  -> 通过后生成或更新 content_items
  -> 前台自动展示
```

如果资料被退回，应保留退回原因，并允许老师基于原记录继续修改后再次提交。

## 6. 数据设计原则

建议保留现有 `content_items` 作为前台展示数据源。

原因是当前前台页面已经围绕 `content_items` 运行，如果让前台直接读取低代码原始表单，会导致展示逻辑越来越复杂，也容易破坏现有页面效果。

推荐采用双层数据结构：

```text
低代码模板层
  lowcode_forms
  lowcode_form_versions

低代码填报层
  lowcode_records
  lowcode_record_assets

前台展示层
  content_items
  content_assets
```

低代码表负责保存“用户填了什么”，`content_items` 负责保存“前台展示什么”。

## 7. 固定专题板块

创新育人专题建议固定以下板块，后台模板围绕这些板块配置：

| 顺序 | 板块 | key | 用途 |
| ---: | --- | --- | --- |
| 1 | 专题概况 | overview | 展示专题背景、建设目标、整体介绍 |
| 2 | 专业群布局 | majors | 展示专业设置、课程体系、就业方向 |
| 3 | 实训场景 | training | 展示实训基地、设备、教学场景 |
| 4 | 产教协同 | cooperation | 展示校企合作、订单班、共同体建设 |
| 5 | 名师名匠 | masters | 展示教师、技能大师、团队介绍 |
| 6 | 优秀校友 | alumni | 展示校友人物、就业成果、成长故事 |
| 7 | 优秀学生 | students | 展示学生典型、竞赛经历、成长案例 |
| 8 | 专题成果 | achievements | 展示教学成果、项目成果、建设成果 |
| 9 | 技能大赛 | competitions | 展示赛事、获奖、承办活动 |
| 10 | 荣誉资质 | honors | 展示证书、奖项、资质认定 |
| 11 | 视频资源 | media | 展示宣传片、访谈、纪实视频 |

如果后续还要纳入“同心校园文化”，建议作为专题大类，而不是强行塞进某一个系部板块。

## 8. 资料类型与抽屉模板

由于不同资料的图片数量、文字数量差异很大，抽屉详情不建议只有一种排版。后台可以固定资料类型，前台按类型自动选择抽屉模板。

推荐固定以下资料类型：

| 类型 | key | 适合内容 | 前台展示建议 |
| --- | --- | --- | --- |
| 普通图文 | article | 概况、介绍、说明类内容 | 文字优先，图片轮播辅助 |
| 人物介绍 | profile | 教师、学生、校友、工匠 | 左右信息结构，头像或人物图原比例显示 |
| 活动纪实 | event | 活动、会议、实践、比赛 | 时间地点信息靠前，多图轮播 |
| 荣誉成果 | honor | 奖项、证书、成果认定 | 证书图片原比例展示，说明文字简洁 |
| 实训场景 | scene | 基地、设备、课堂场景 | 大图轮播，文字分段说明 |
| 视频资料 | video | 宣传片、访谈、纪实视频 | 视频优先，文字和附件辅助 |
| 附件资料 | attachment | PDF、Word、Excel、PPT、压缩包 | 附件列表清晰展示，不伪装成图片 |

前台原则：

- 图片统一使用原比例缩放，不强行裁剪。
- 多图使用自动轮播，避免页面被图片撑乱。
- 图片数量不确定时，右侧只展示一张当前图片，按时间切换下一张。
- 文字较多时抽屉内容必须可滚动。
- 不同类型资料使用不同信息密度，避免人物类、活动类、荣誉类全部挤成一种样子。

## 9. 模板字段建议

模板字段不要无限开放，第一阶段固定常用控件即可。

推荐字段控件：

- 单行文本。
- 多行文本。
- 富文本。
- 数字。
- 日期。
- 单选。
- 多选。
- 图片上传。
- 视频上传。
- 附件上传。
- 链接。

字段配置建议支持：

- 字段名称。
- 字段 key。
- 是否必填。
- 提示语。
- 默认值。
- 最大字数。
- 正则校验。
- 分组。
- 排序。
- 是否映射到前台标题、摘要、正文、封面、媒体资源。

## 10. 权限与角色

建议第一阶段只区分三类角色：

| 角色 | 权限 |
| --- | --- |
| 管理员 | 配置模板、审核资料、发布资料、查看统计 |
| 系部管理员 | 管理本系部资料、审核本系部提交内容 |
| 老师 | 按模板填报、保存草稿、提交审核、修改退回内容 |

权限不宜第一阶段做得过细，否则后台复杂度会上升很快。

## 11. 改造难度评估

整体难度：**中等，可控**。

它不是简单加几个字段，但也不需要推倒重做。主要难点在于数据映射、审核闭环和后台交互整理。

| 模块 | 难度 | 风险 | 建议 |
| --- | --- | --- | --- |
| 模板配置 | 中 | 中 | 先固定控件，再逐步增加高级能力 |
| 动态表单渲染 | 中 | 中 | 只在后台使用，不影响前台展示 |
| 数据库新增低代码表 | 中 | 低 | 新增表，不破坏旧表 |
| 映射到 `content_items` | 中 | 高 | 必须保持前台展示数据稳定 |
| 审核和退回修改 | 中 | 中 | 沿用现有审核逻辑，补齐状态流转 |
| 素材归档 | 中 | 中 | 图片、视频、附件分角色管理 |
| 前台抽屉适配 | 中 | 中 | 只补类型模板，不重做整体布局 |
| 通用页面拖拽搭建器 | 高 | 高 | 第一阶段不做 |

## 12. 分阶段实施计划

### 第一阶段：稳定资料采集闭环

目标是能用起来。

- 建立资料采集模板。
- 支持老师按模板填报。
- 支持草稿、提交、审核、退回。
- 支持图片、视频、附件上传。
- 填报后自动生成 `content_items`。
- 前台保持现有展示样式。

### 第二阶段：后台体验优化

目标是让管理更顺。

- 模板复制。
- 模板版本管理。
- 模板导入导出。
- 填报预览。
- 资料明细导出。
- 专题完整度统计。
- 板块覆盖率检查。
- 素材归档导出。

### 第三阶段：质量规则和报表

目标是让资料更规范。

- 按板块配置质量检查规则。
- 检查标题、摘要、正文、图片、视频、附件是否缺失。
- 按系部、专题、老师统计提交情况。
- 导出资料质量报表。
- 对长期缺失资料进行提醒。

### 第四阶段：谨慎扩展低代码能力

目标是增强灵活性，但不破坏前台。

- 增加更多字段控件。
- 增加字段联动。
- 增加简单条件显示。
- 增加更细权限。
- 增加更多抽屉展示类型。

第一阶段和第二阶段完成后，再判断是否需要继续扩展，避免为了“低代码”而把系统复杂度拉得过高。

## 13. 风险控制

### 13.1 前台效果被破坏

风险：低代码字段过多、展示映射混乱，导致前台卡片和抽屉排版变差。

控制方式：

- 前台不直接渲染任意字段。
- 后台字段必须映射到固定展示槽位。
- 抽屉模板按资料类型固定。

### 13.2 老师不会用

风险：后台配置项过多，普通填报用户理解困难。

控制方式：

- 老师只看到填写界面。
- 模板配置只给管理员使用。
- 字段提示语写清楚。
- 必填和格式错误即时提示。

### 13.3 资料越积越乱

风险：图片、视频、附件没有归档规则，后期难维护。

控制方式：

- 素材绑定资料记录。
- 素材区分图片、视频、附件角色。
- 后台提供素材归档导出。
- 大素材继续放网盘，不直接进入 Git 仓库。

### 13.4 工程量失控

风险：一开始就做通用页面搭建器、流程引擎、复杂权限，导致项目周期变长。

控制方式：

- 第一阶段只做资料采集模板。
- 不做前台自由拖拽。
- 不做自定义 CSS。
- 不做万能建表器。
- 优先复用现有 `content_items` 和审核发布逻辑。

## 14. 最终建议

建议把当前项目的低代码能力定义为：

**面向学校展示资料的低代码采集与发布系统。**

它的价值不是让每个用户都能设计页面，而是让学校、系部、专题资料能够用统一规则快速录入、审核、发布，并继续保持当前已经形成的前台展示质感。

推荐当前开发策略：

```text
少动前台
稳住展示
补强后台
规范资料
逐步报表化
```

这样既能满足“低代码快速开发业务功能”的要求，也能最大程度保护现在已经做好的页面效果。
