# 低代码快速开发业务功能实施方案

## 1. 背景与目标

当前系统已经形成了较完整的展示体系，包括欢迎页、学校门户、系部门户、创新育人专题、专题卡片、无缝循环滚动、抽屉详情页、二维码详情页等。后续低代码改造的核心目标，不是把前台展示页面改造成自由拖拽式页面搭建器，而是在后台增加一套可配置的资料采集和业务表单能力。

本阶段目标可以概括为：

```text
后台低代码配置资料采集模板
  -> 老师或管理员按模板录入资料
  -> 系统自动生成结构化展示数据
  -> 进入审核和发布流程
  -> 前台继续使用现有展示样式呈现
```

这样既能满足“低代码快速开发业务功能”的要求，也能最大限度保护当前已经调好的前端展示效果。

## 2. 产品定位

建议后台模块命名为：

**资料采集模板**

不建议第一阶段直接命名为“低代码平台”。原因是学校实际使用场景更关注资料是否规范、是否好填、是否能统一展示，而不是让每个使用者都去设计页面。模块命名应让老师和管理员一看就知道用途，降低理解成本。

推荐后台形成以下逻辑：

```text
项目 / 门户
  -> 系部 / 专题
  -> 板块
  -> 资料采集模板
  -> 填写资料
  -> 上传图片 / 视频
  -> 提交审核
  -> 发布展示
```

## 3. 改造边界

### 3.1 第一阶段要做

- 管理员可以创建、复制、启停资料采集模板。
- 模板可以绑定项目、系部、专题板块、资料类型。
- 模板字段支持文本、长文本、富文本、数字、日期、单选、多选、图片、视频、附件等基础控件。
- 字段支持必填、提示语、默认值、最大字数、格式校验、排序、分组。
- 老师可以按模板填写资料并保存草稿。
- 老师提交后进入审核流程。
- 管理员提交的资料可以按权限直接通过。
- 提交后的资料自动映射到现有 `content_items`。
- 前台继续读取 `content_items` 展示，不直接读取低代码原始表单。
- 图片和视频继续使用现有素材管理逻辑。
- 抽屉详情页继续使用现有类型化展示模板。

### 3.2 第一阶段不做

- 不做前台页面自由拖拽。
- 不做老师自定义页面布局。
- 不做自定义 CSS。
- 不做复杂流程引擎。
- 不做万能数据库建表器。
- 不做复杂公式引擎。
- 不让字段直接控制前台视觉样式。
- 不推翻现有学校门户、系部门户、专题页和抽屉详情页。

第一阶段的原则是：**低代码只负责后台资料怎么录入，前台继续负责统一展示。**

## 4. 总体架构

建议采用“双层数据结构”：

```text
低代码模板层
  lowcode_forms
  lowcode_form_versions

低代码填报层
  lowcode_records
  lowcode_record_assets

展示数据层
  content_items
  content_assets / 现有素材关系
```

### 4.1 为什么要保留 `content_items`

`content_items` 是当前前台展示的稳定数据源。学校门户、系部门户、专题卡片、循环滚动、抽屉详情等功能已经围绕它运行。如果让前台直接读取各种动态表单，会导致展示逻辑越来越复杂，后期维护风险变大。

因此低代码表单提交后，应由后端统一把表单内容整理成 `content_items` 所需的数据结构。前台保持稳定，后台变得灵活。

### 4.2 推荐数据流

```text
管理员配置模板
  -> 生成模板版本
  -> 老师按模板填写资料
  -> 保存草稿 / 提交审核
  -> 后端校验字段
  -> 生成或更新 content_items
  -> 进入审核发布
  -> 前台自动展示
```

## 5. 模板设计

### 5.1 固定板块

创新育人专题建议固定以下板块：

| 序号 | 板块 | key | 说明 |
|---:|---|---|---|
| 1 | 专题概况 | overview | 专题背景、建设目标、整体介绍 |
| 2 | 专业群布局 | majors | 专业设置、课程体系、就业方向 |
| 3 | 实训场景 | training | 实训基地、设备、教学场景 |
| 4 | 产教协同 | cooperation | 校企合作、订单班、共同体 |
| 5 | 名师名匠 | masters | 教学名师、技能大师、教师团队 |
| 6 | 优秀校友 | alumni | 校友人物、就业成果、成长故事 |
| 7 | 优秀学生 | students | 学生人物、竞赛经历、成长案例 |
| 8 | 专题成果 | achievements | 教学成果、项目成果、建设成果 |
| 9 | 技能大赛 | competitions | 赛事、获奖、承办活动 |
| 10 | 荣誉资质 | honors | 证书、奖项、资质认定 |
| 11 | 视频资源 | media | 宣传片、访谈、纪实视频 |

这些板块是展示结构，不建议让老师随意新增。后台可以允许管理员调整名称和排序，但前台应保持统一展示模型。

### 5.2 内容类型

建议资料类型固定为以下几类：

| 类型 | key | 适合内容 | 抽屉展示方式 |
|---|---|---|---|
| 图文资料 | article | 概况、介绍、说明 | 正文为主，图片轮播辅助 |
| 人物资料 | person | 名师、校友、学生 | 图片与人物信息并排，经历分段 |
| 活动资料 | activity | 比赛、合作、实践活动 | 时间地点信息优先，图片轮播 |
| 场景资料 | scene | 实训基地、设备、空间 | 图片优先，文字分区说明 |
| 成果资料 | achievement | 项目成果、教学成果 | 成果摘要、指标、附件 |
| 荣誉资料 | honor | 证书、奖项、资质 | 证书图轮播，文字说明 |
| 视频资料 | video | 宣传片、访谈、纪录片 | 视频优先，简介辅助 |

低代码模板只决定“资料怎么填”，内容类型决定“抽屉怎么展示”。

## 6. 后台功能设计

### 6.1 管理员视角

管理员需要完成三类工作：

- 配置模板：决定每类资料需要填哪些字段。
- 管理记录：查看老师提交的草稿、待审、已发布、驳回记录。
- 审核发布：对资料进行审核、退回、发布、下架。

后台建议提供：

- 模板列表。
- 模板复制。
- 模板版本记录。
- 字段拖拽排序。
- 字段分组。
- 字段校验。
- 预览填写效果。
- 提交记录筛选。
- CSV 导出。
- 草稿清理。

### 6.2 老师视角

老师不应该接触复杂配置，只需要看到：

- 选择要填报的专题或板块。
- 选择资料模板。
- 按字段填写内容。
- 上传图片、视频、附件。
- 保存草稿。
- 提交审核。
- 查看审核状态和退回原因。

老师端的核心体验应该像“填规范表单”，而不是“搭页面”。

## 7. 前台展示策略

前台尽量不因低代码改造而大改。

建议保持：

- `/display` 作为统一顶部栏和主展示风格参考。
- 欢迎页、学校门户页展示学校官网二维码。
- 其他详情页不重复展示学校官网二维码。
- 系部门户顶部栏统一校徽样式。
- 专题页继续使用卡片和无缝循环滚动。
- 抽屉详情页继续使用原比例图片轮播。
- 图片使用“完整显示优先”，避免裁剪。
- 多图采用自动轮播，而不是一次性堆叠导致拥挤。

不同资料类型只做抽屉内部布局差异，不影响外层页面结构。

## 8. 数据库改造建议

### 8.1 模板表

`lowcode_forms`

用于保存模板基础信息：

- 模板名称
- 绑定项目
- 绑定板块
- 绑定内容类型
- 启用状态
- 字段 schema
- 映射规则
- 创建人
- 更新时间

### 8.2 模板版本表

`lowcode_form_versions`

用于保存每次模板变更记录：

- 模板 ID
- 版本号
- 字段 schema 快照
- 映射规则快照
- 修改说明
- 创建时间

### 8.3 填报记录表

`lowcode_records`

用于保存老师或管理员填写的表单数据：

- 模板 ID
- 模板版本号
- 项目 ID
- 填报人
- 表单 JSON
- 状态：草稿、待审、已通过、已驳回
- 关联 `content_item_id`
- 提交时间
- 审核时间
- 驳回原因

### 8.4 素材关系表

`lowcode_record_assets`

用于记录表单和素材之间的关系：

- 记录 ID
- 素材路径
- 素材类型
- 所属字段
- 排序
- 说明

## 9. 实施阶段

### 阶段一：最小可用

目标：让管理员能配置模板，老师能填报，前台能展示。

范围：

- 新增低代码模板表。
- 新增填报记录表。
- 后台增加模板配置入口。
- 后台增加模板填写入口。
- 提交后生成 `content_items`。
- 接入现有审核和发布。

验收标准：

- 管理员能创建一个“名师名匠”模板。
- 老师能按模板提交人物资料。
- 提交后能在后台审核。
- 审核通过后能在专题页卡片和抽屉详情里展示。

### 阶段二：体验完善

目标：降低老师填写成本，提升管理员维护效率。

范围：

- 草稿保存。
- 模板复制。
- 模板版本恢复。
- 字段分组。
- 字数限制。
- 正则校验。
- 提交记录筛选。
- 记录导出。
- 图片批量上传。

验收标准：

- 老师中途退出后可以继续填写草稿。
- 管理员误改模板后可以恢复旧版本。
- 管理员可以快速筛选待审资料。
- 导出的记录能用于线下汇总。

### 阶段三：业务扩展

目标：在不破坏展示系统的前提下支持更多业务。

范围：

- 更多模板预设。
- 模板导入导出。
- 附件资料归档。
- 按系部统计资料完整度。
- 按专题统计资料数量。
- 退回修改闭环。
- 展示数据质量检查。

验收标准：

- 每个系部能看到自己缺哪些板块资料。
- 管理员能导出专题建设资料清单。
- 资料退回后老师能按意见修改并重新提交。

## 10. 改造难度评估

整体难度：**中等，可控。**

原因是当前项目已经有展示、素材、审核、后台基础，低代码改造不需要从零搭系统。但需要谨慎处理数据库结构、模板版本、表单校验和 `content_items` 映射。

| 模块 | 难度 | 风险 | 建议 |
|---|---:|---:|---|
| 模板字段配置 | 中 | 中 | 先支持基础控件和字段排序 |
| 动态表单填写 | 中 | 中 | 后台使用统一渲染逻辑 |
| 模板版本管理 | 中 | 中 | 每次保存生成版本快照 |
| 映射到 `content_items` | 中 | 高 | 保持前台数据结构稳定 |
| 图片和视频关联 | 中 | 中 | 继续复用现有素材体系 |
| 审核发布接入 | 中 | 中 | 沿用现有状态流转 |
| 前台展示适配 | 低 | 中 | 只补兼容，不重写页面 |
| 页面自由搭建 | 高 | 高 | 第一阶段不做 |

## 11. 风险控制

### 11.1 避免前台失控

所有前台页面继续使用固定模板。低代码字段不能直接改变页面结构、颜色、动画、布局，只能提供内容数据。

### 11.2 避免数据混乱

模板字段必须有稳定 key，不能随意重名。模板变更需要保存版本，历史记录继续按提交时的模板版本解析。

### 11.3 避免老师使用复杂

老师端只保留填写、上传、保存、提交、查看状态。模板配置、字段映射、版本恢复等功能只给管理员。

### 11.4 避免素材失控

大素材继续放网盘或 `uploads/` 本地目录，不进入 Git 仓库。仓库只保存代码、数据库快照和必要说明文档。

## 12. 推荐结论

建议按“后台低代码资料采集，前台固定模板展示”的路线推进。

这条路线对现有项目破坏最小，也最符合当前展示系统的实际状态。第一阶段重点不是做一个万能平台，而是把资料上传、字段规范、审核发布、前台展示这条链路做顺。等这条链路稳定后，再逐步扩展模板导入导出、统计报表、资料完整度检查等能力。

最终系统应形成这样的能力：

```text
管理员配置规范
老师按规范填资料
系统自动生成展示数据
审核后统一展示
后续资料可持续维护
```

这比一开始追求“大而全”的低代码平台更稳，也更适合当前项目继续迭代。
