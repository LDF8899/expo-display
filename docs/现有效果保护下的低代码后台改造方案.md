# 现有效果保护下的低代码后台改造方案

## 1. 核心判断

当前项目已经形成了比较明确的前台展示方向，包括学校门户、系部门户、创新育人专题、专题卡片、资料抽屉、图片轮播、扫码详情页等。现阶段最重要的不是把系统改成一个通用低代码建站平台，而是在不破坏现有展示效果的前提下，把后台资料采集、审核、发布流程做得更规范、更低门槛。

推荐方向：

```text
前台保持现有展示模板
后台增加资料采集模板
老师按模板填资料
管理员审核和发布
系统自动映射到现有 content_items 展示数据
```

一句话总结：

> 低代码能力应该服务于资料录入和业务表单配置，而不是让每个人自由设计前台页面。

这样既能满足“低代码快速开发业务功能”的要求，也能最大程度保护目前已经调好的页面效果。

## 2. 为什么不建议大改

如果直接把项目改成通用低代码平台，会带来几个明显风险：

- 前台视觉容易失控，不同老师配置出来的页面风格不统一。
- 数据结构会变复杂，后期审核、维护、迁移都会变困难。
- 页面自由拖拽、自由布局、自定义样式会显著增加开发量。
- 当前已经完成的门户页、专题页、抽屉页可能被新逻辑冲乱。
- 老师实际需要的是“按规范提交资料”，不是学习一个复杂页面搭建器。

所以本项目更适合做成：

```text
固定展示模板 + 可配置资料表单 + 统一审核发布
```

这是更稳、更省工程量，也更符合学校展示系统实际使用场景的路线。

## 3. 产品定位

后台模块建议命名为：

**资料采集模板**

不建议直接叫“低代码平台”。“低代码平台”对使用者来说过于技术化，也容易让人误解成可以随意拖拽页面、任意设计样式。

“资料采集模板”更贴近真实业务：

- 管理员定义资料该怎么填。
- 老师按照模板提交文字、图片、视频、附件。
- 系统自动检查资料是否完整。
- 审核通过后自动进入前台展示。

## 4. 改造边界

### 4.1 第一阶段要做

- 固定创新育人专题板块。
- 固定资料类型和抽屉展示类型。
- 后台支持模板化资料填报。
- 管理员可以配置字段、必填项、提示语、映射目标。
- 老师只负责填报，不参与页面设计。
- 支持图片、视频、附件上传。
- 支持保存草稿、提交审核、退回修改、重新提交。
- 审核通过后生成或更新 `content_items`。
- 前台继续使用现有页面样式和展示逻辑。

### 4.2 第一阶段不做

- 不做前台页面自由拖拽。
- 不做自定义 CSS。
- 不做万能建表器。
- 不做复杂流程引擎。
- 不允许老师修改前台布局。
- 不推翻现有门户页和专题页。

## 5. 后台信息架构建议

后台可以逐步整理成以下结构：

```text
首页概览
  -> 待审核资料
  -> 资料完整度
  -> 最近更新
  -> 超期提醒

门户管理
  -> 学校门户
  -> 系部门户
  -> 创新育人专题

资料采集模板
  -> 模板列表
  -> 新建模板
  -> 复制模板
  -> 版本管理
  -> 启用 / 停用

资料填报
  -> 按模板填报
  -> 保存草稿
  -> 提交审核
  -> 退回修改

资料审核
  -> 待审核
  -> 已通过
  -> 已退回
  -> 已发布

素材管理
  -> 图片
  -> 视频
  -> 附件
  -> 素材归档

质量检查
  -> 专题完整度
  -> 板块覆盖情况
  -> 图片缺失检查
  -> 文字长度检查
  -> 附件缺失检查
```

这个结构的重点是让后台从“功能堆叠”变成“资料生命周期管理”。

## 6. 角色设计

第一阶段建议只保留三类角色，避免权限体系过早复杂化。

| 角色 | 主要职责 |
| --- | --- |
| 超级管理员 | 管理全部门户、模板、用户、审核、发布、系统配置 |
| 系部管理员 | 管理本系部资料，审核本系部老师提交的内容 |
| 老师 | 按模板填报资料，保存草稿，提交审核，修改退回内容 |

权限原则：

- 超级管理员看全局。
- 系部管理员只看本系部。
- 老师只看自己负责和自己提交的资料。
- 模板配置入口不开放给普通老师。

## 7. 固定专题板块

创新育人专题建议固定以下板块，后台模板围绕这些板块配置：

| 顺序 | 板块 | key | 说明 |
| ---: | --- | --- | --- |
| 1 | 专题概况 | overview | 专题背景、建设目标、整体介绍 |
| 2 | 专业群布局 | majors | 专业设置、课程体系、就业方向 |
| 3 | 实训场景 | training | 实训基地、设备、教学场景 |
| 4 | 产教协同 | cooperation | 校企合作、订单班、共同体建设 |
| 5 | 名师名匠 | masters | 教学名师、技能大师、教师团队 |
| 6 | 优秀校友 | alumni | 校友人物、就业成果、成长故事 |
| 7 | 优秀学生 | students | 学生典型、竞赛经历、成长案例 |
| 8 | 专题成果 | achievements | 教学成果、项目成果、建设成果 |
| 9 | 技能大赛 | competitions | 赛事、获奖、承办活动 |
| 10 | 荣誉资质 | honors | 证书、奖项、资质认定 |
| 11 | 视频资源 | media | 宣传片、访谈、纪实视频 |

“同心校园文化”建议作为独立专题大类处理，不强行塞进某个系部板块。

## 8. 资料类型与抽屉展示

由于不同资料的图片数量、文字量差异很大，抽屉详情不建议只用一种排版。后台可以固定资料类型，前台按类型选择展示模板。

| 类型 | key | 适合内容 | 展示建议 |
| --- | --- | --- | --- |
| 普通图文 | article | 概况、介绍、说明类内容 | 文字优先，图片轮播辅助 |
| 人物介绍 | profile | 教师、学生、校友、工匠 | 人物信息靠前，图片原比例展示 |
| 活动纪实 | event | 活动、会议、实践、比赛 | 时间地点靠前，多图轮播 |
| 荣誉成果 | honor | 奖项、证书、成果认定 | 证书图片原比例展示，文字简洁 |
| 实训场景 | scene | 基地、设备、课堂场景 | 大图轮播，文字分段说明 |
| 视频资料 | video | 宣传片、访谈、纪实视频 | 视频优先，文字和附件辅助 |
| 附件资料 | attachment | PDF、Word、Excel、PPT、压缩包 | 附件列表清晰展示 |

前台展示原则：

- 图片统一使用原比例缩放，不强行裁剪。
- 多张图片使用自动轮播，避免页面被图片数量撑乱。
- 图片数量不固定时，右侧只展示一张当前图片，按时间自动切换。
- 文字较多时，抽屉内容区域必须可滚动。
- 人物类、活动类、荣誉类使用不同信息密度，不全部挤成一种版式。

## 9. 表单字段设计

第一阶段字段控件不要无限开放，先支持常用能力即可。

推荐控件：

- 单行文本
- 多行文本
- 富文本
- 数字
- 日期
- 下拉选择
- 单选
- 多选
- 图片上传
- 视频上传
- 附件上传
- 链接

字段配置建议包含：

- 字段名称
- 字段 key
- 字段类型
- 是否必填
- 提示语
- 默认值
- 最大字数
- 校验规则
- 字段分组
- 排序
- 映射目标

字段分组建议：

```text
基础信息
  标题、副标题、摘要、所属板块、资料类型

正文内容
  正文、人物介绍、活动说明、成果说明、时间地点

媒体素材
  封面图、图集、视频、附件

展示设置
  排序、是否重点展示、是否启用
```

## 10. 数据设计原则

建议继续保留 `content_items` 作为前台展示主数据源。

低代码表单只作为后台资料采集层：

```text
lowcode_forms
  -> lowcode_form_versions
  -> lowcode_records
  -> lowcode_record_assets
  -> content_items
  -> 前台门户 / 专题页 / 抽屉详情
```

这样前台不需要知道资料是普通编辑器录入的，还是通过低代码表单录入的。前台只负责稳定展示结构化后的内容。

推荐新增或完善的数据对象：

| 数据对象 | 作用 |
| --- | --- |
| `lowcode_forms` | 保存资料采集模板基础信息 |
| `lowcode_form_versions` | 保存模板字段版本 |
| `lowcode_records` | 保存老师填报的原始记录 |
| `lowcode_record_assets` | 保存记录与图片、视频、附件的关系 |
| `content_items` | 保持现有前台展示数据 |
| `content_assets` | 保持现有素材关联数据 |

## 11. 审核发布流程

推荐流程：

```text
老师填写资料
  -> 保存草稿
  -> 提交审核
  -> 系部管理员初审
  -> 超级管理员复核或直接发布
  -> 生成 / 更新 content_items
  -> 前台自动展示
```

如果当前阶段不想做两级审核，可以先做：

```text
老师提交
  -> 管理员审核
  -> 通过后发布
```

后续再把“系部管理员初审”补上。

退回修改时要保留：

- 退回原因
- 退回时间
- 审核人
- 原填报内容
- 再次提交记录

## 12. 改造难度评估

整体难度：**中等，可控**。

它不是简单加几个字段，但也不需要推翻重做。真正要谨慎的是数据映射、审核闭环和后台交互整理。

| 模块 | 难度 | 风险 | 建议 |
| --- | --- | --- | --- |
| 模板配置 | 中 | 中 | 先固定控件，再逐步扩展 |
| 动态表单渲染 | 中 | 中 | 只在后台使用，不影响前台 |
| 新增低代码表 | 中 | 低 | 新增表，不破坏旧表 |
| 映射到 `content_items` | 中 | 高 | 必须复用现有展示结构 |
| 审核和退回修改 | 中 | 中 | 沿用现有审核逻辑 |
| 素材归档 | 中 | 中 | 图片、视频、附件统一关联 |
| 前台抽屉适配 | 中 | 中 | 只补类型模板，不重做页面 |
| 通用页面拖拽 | 高 | 高 | 第一阶段不做 |

## 13. 分阶段实施路线

### 阶段一：稳定资料采集闭环

目标是先能用起来。

- 建立资料采集模板。
- 支持老师按模板填报。
- 支持草稿、提交、审核、退回。
- 支持图片、视频、附件上传。
- 填报后自动生成 `content_items`。
- 前台保持现有展示样式。

### 阶段二：后台体验优化

目标是让管理更顺。

- 模板复制。
- 模板版本管理。
- 模板导入导出。
- 填报预览。
- 资料明细导出。
- 专题完整度统计。
- 板块覆盖率检查。
- 素材归档导出。

### 阶段三：质量规则和报表

目标是让资料更规范。

- 按板块配置质量检查规则。
- 检查标题、摘要、正文、图片、视频、附件是否缺失。
- 按系部、专题、老师统计提交情况。
- 导出资料质量报表。
- 对长期缺失资料进行提醒。

### 阶段四：谨慎扩展低代码能力

目标是在系统稳定后增强灵活性。

- 增加更多字段控件。
- 增加字段联动。
- 增加条件显示。
- 增加更细权限。
- 增加更多抽屉展示类型。

只有阶段一和阶段二稳定后，才建议进入阶段四。

## 14. 验收标准

第一阶段完成后，至少满足以下标准：

- 老师可以不接触页面配置，只通过模板提交资料。
- 管理员可以新增、复制、启用、停用资料模板。
- 资料可以保存草稿、提交审核、退回修改、审核通过。
- 审核通过后前台能自动展示。
- 图片、视频、附件能和资料记录绑定。
- 前台门户页、专题页、抽屉页不因后台改造发生明显视觉退化。
- 大素材仍保留在 `uploads/` 或网盘，不进入 Git 仓库。
- 数据库改造有备份，有初始化脚本，有基础检查。

## 15. 当前最推荐的下一步

建议下一步不要继续扩前台新样式，而是先把后台的数据入口固定下来：

```text
固定板块
  -> 固定资料类型
  -> 固定抽屉模板
  -> 固定字段映射
  -> 完成填报审核闭环
  -> 再优化前台局部细节
```

这条路线比较稳。它不会把现有页面推翻重来，也能逐步满足低代码业务功能的要求。

## 16. 最终建议

本项目的低代码改造应该定义为：

**面向学校展示资料的低代码采集与发布系统。**

它的价值不是让每个人都能设计页面，而是让学校、系部、专题资料能够用统一规则快速录入、审核、发布，并继续保持当前已经形成的前台展示质感。

当前开发策略建议坚持：

```text
少动前台
稳住展示
补强后台
规范资料
逐步报表化
```

这样既能满足低代码快速开发业务功能，也能避免因为过度改造把现有项目改乱。
