# 后台资料规范化改造计划书

## 1. 改造目标

当前前端展示方向已经基本确定：学校门户、专题门户、系部门户、卡片轮播、详情抽屉、大屏扫码详情页都以固定视觉体系呈现。下一阶段的核心不是继续让后台自由编辑页面，而是建立一套稳定的资料管理模型。

本次改造目标：

- 固定专题 11 个标准板块。
- 后台按“资料类型”上传内容，而不是按网页排版上传内容。
- 前端根据资料类型自动套用抽屉模板。
- 图片数量、文字长度不再影响后台录入方式，由前端负责自适应展示。
- 保留现有 `projects / pages / assets / review` 基础能力，分阶段升级，避免一次性推翻。

## 2. 固定专题板块

专题门户统一固定为 11 个板块：

| 顺序 | 板块名称 | key | 主要内容 |
| --- | --- | --- | --- |
| 1 | 专题概况 | overview | 专题背景、建设目标、总体介绍 |
| 2 | 专业群布局 | majors | 专业群、专业方向、课程、就业方向 |
| 3 | 实训场景 | training | 实训基地、实训室、设备、实践教学 |
| 4 | 产教协同 | cooperation | 校企合作、订单班、共同体、社会服务 |
| 5 | 名师名匠 | masters | 教学名师、技能大师、教师团队 |
| 6 | 优秀校友 | alumni | 校友人物、成长经历、就业成果 |
| 7 | 优秀学生 | students | 学生人物、竞赛经历、成长故事 |
| 8 | 专题成果 | achievements | 教学成果、项目成果、典型案例 |
| 9 | 技能大赛 | competitions | 赛事、获奖、承办活动、比赛现场 |
| 10 | 荣誉资质 | honors | 证书、奖项、资质、认定结果 |
| 11 | 视频资源 | media | 视频、宣传片、访谈、纪实片 |

后续新增资料只允许归入这 11 个板块，不再随意新增专题前台板块。

## 3. 抽屉资料类型

板块固定，但抽屉模板不固定为一种。每条资料需要选择一个资料类型，前端按类型自动排版。

| 类型 | key | 适用板块 | 抽屉展示逻辑 |
| --- | --- | --- | --- |
| 人物类 | person | 名师名匠、优秀校友、优秀学生 | 图片在人物介绍旁边；姓名、身份、简介、事迹分组展示；多人纵向排列 |
| 活动类 | activity | 实训场景、产教协同、技能大赛 | 标题、时间地点、正文段落；图片跟随段落或作为单图轮播 |
| 荣誉类 | honor | 荣誉资质、技能大赛、专题成果 | 证书/奖状优先展示；旁边或下方显示奖项、级别、年份、获奖单位 |
| 成果类 | achievement | 专题成果、专业群布局、产教协同 | 摘要和关键指标优先；下方展示成果说明、图片、证书、案例 |
| 场景类 | scene | 实训场景、专业群布局 | 场景名称、功能定位、服务课程、设备条件；图片原比例轮播 |
| 视频类 | video | 视频资源 | 视频封面/播放器为主；下方展示视频说明、时长、适用场景 |
| 普通图文类 | article | 专题概况及兜底资料 | 标题、摘要、正文、图片轮播；适合不好归类的内容 |

后台不暴露“左图右文、三列图、瀑布流”等排版选项，只让用户选择资料类型。

## 4. 后台录入规范

每条资料统一包含以下字段：

- 所属门户：专题 / 系部 / 学校。
- 所属板块：固定板块 key。
- 资料类型：person / activity / honor / achievement / scene / video / article。
- 标题：必填。
- 副标题 / 摘要：可选，但建议填写。
- 正文段落：支持多段文本。
- 图片组：支持批量上传、拖拽排序、填写说明。
- 视频组：支持视频地址、封面图、标题、时长。
- 关键字段：按资料类型显示不同字段。
- 排序：控制同一板块内显示顺序。
- 是否重点展示：控制卡片摘要优先级。
- 状态：草稿、待审、已通过、已驳回、已发布。

不同资料类型的推荐字段：

| 类型 | 推荐字段 |
| --- | --- |
| 人物类 | 姓名、身份/职务、专业/班级、荣誉标签、个人简介、主要事迹 |
| 活动类 | 活动名称、时间、地点、主办/参与单位、活动说明、成果 |
| 荣誉类 | 荣誉名称、级别、年份、获奖单位/个人、证书图片 |
| 成果类 | 成果名称、成果级别、建设周期、参与团队、关键指标、成果说明 |
| 场景类 | 场景名称、功能定位、服务课程、设备条件、开放对象 |
| 视频类 | 视频标题、封面、视频地址、时长、简介 |
| 普通图文类 | 标题、摘要、正文、图片组 |

## 5. 数据库改造建议

保留现有核心表：

- `projects`：门户项目。
- `pages`：现有扫码详情页和兼容层。
- `assets`：素材库。
- `page_versions / project_versions`：审核版本。
- `deployed_pages`：发布范围。

新增结构化资料表。

### 5.1 content_items

用于保存一条结构化资料。

建议字段：

- `id`
- `project_id`
- `module_key`
- `content_type`
- `title`
- `subtitle`
- `summary`
- `body_json`
- `meta_json`
- `cover_asset_id`
- `sort_order`
- `featured`
- `enabled`
- `review_status`
- `pending_version_id`
- `submitted_by`
- `reviewed_by`
- `review_note`
- `created_at`
- `updated_at`

说明：

- `body_json` 保存段落、列表、小标题等结构化正文。
- `meta_json` 保存人物身份、荣誉年份、活动地点等类型字段。
- `cover_asset_id` 指向封面素材。

### 5.2 content_item_assets

用于保存资料和素材的多对多关系。

建议字段：

- `id`
- `content_item_id`
- `asset_id`
- `role`
- `caption`
- `sort_order`
- `created_at`

`role` 可选：

- cover
- gallery
- certificate
- portrait
- video
- attachment

### 5.3 content_item_versions

用于资料审核草稿。

建议字段：

- `id`
- `content_item_id`
- `project_id`
- `operation`
- `status`
- `snapshot_json`
- `submitted_by`
- `submitted_at`
- `reviewed_by`
- `reviewed_at`
- `review_note`
- `changes`

### 5.4 兼容现有 pages

短期内不删除 `pages`。

过渡策略：

- 新资料保存到 `content_items`。
- 后端自动生成或同步一条 `pages` 记录，用于现有 `/display?project=...&code=...` 扫码详情。
- 前端专题门户优先读取结构化资料；读取不到时继续使用现有 blueprint JSON / pages 数据。

这样既能向新模型迁移，也不影响已有扫码大屏。

## 6. 后端接口改造

### 6.1 模板接口

新增：

- `GET /api/content/templates`

返回：

- 固定 11 个专题板块。
- 7 种资料类型。
- 每种资料类型需要的字段、推荐说明、前端模板 key。

### 6.2 资料管理接口

新增：

- `GET /api/projects/:projectId/content-items`
- `POST /api/projects/:projectId/content-items`
- `GET /api/projects/:projectId/content-items/:id`
- `PUT /api/projects/:projectId/content-items/:id`
- `DELETE /api/projects/:projectId/content-items/:id`

支持按以下条件过滤：

- `module_key`
- `content_type`
- `review_status`
- `enabled`

### 6.3 素材关联接口

新增：

- `POST /api/content-items/:id/assets`
- `PUT /api/content-items/:id/assets/order`
- `DELETE /api/content-items/:id/assets/:assetId`

### 6.4 门户展示接口

新增或增强：

- `GET /api/portal/topics/:slug`
- `GET /api/portal/departments/:slug`

返回统一结构：

```json
{
  "project": {},
  "modules": [
    {
      "key": "students",
      "label": "优秀学生",
      "items": [
        {
          "id": 1,
          "type": "person",
          "title": "文旅筑梦，技耀黔程——韦媛",
          "summary": "...",
          "meta": {},
          "assets": []
        }
      ]
    }
  ]
}
```

### 6.5 扫码详情接口

保留：

- `/display?project=...&code=...`

增强：

- code 可以对应 `pages`，也可以对应 `content_items`。
- 结构化资料由后端转换成前端详情数据。

## 7. 前端展示规则

### 7.1 专题卡片

每个固定板块生成一张卡片。

卡片展示：

- 板块名称。
- 板块摘要。
- 前 3 条重点资料摘要。
- 右侧统一一张主图位。
- 多图按时间轮播。
- 图片保持原比例完整缩放。

### 7.2 抽屉详情

抽屉按资料类型自动选择模板：

- `person`：人物卡片流。
- `activity`：活动图文流。
- `honor`：证书荣誉流。
- `achievement`：成果说明流。
- `scene`：场景介绍流。
- `video`：视频播放流。
- `article`：普通图文流。

通用规则：

- 图片不裁剪。
- 图片多时轮播或纵向分组。
- 文字多时抽屉内部自动滚动。
- 没有图片时不保留空图片区。
- 多条资料时按排序纵向排列。

## 8. 后台页面改造

建议后台改成三段式工作流：

### 8.1 选择门户

选择：

- 学校门户
- 某个专题
- 某个系部

### 8.2 选择板块

专题固定显示 11 个板块。

板块卡片显示：

- 已上传资料数量。
- 已通过数量。
- 是否缺资料。
- 最近更新时间。

### 8.3 编辑资料

资料编辑器显示：

- 资料类型选择。
- 类型字段表单。
- 正文段落编辑。
- 图片/视频上传区。
- 拖拽排序。
- 预览抽屉。
- 保存草稿 / 提交审核 / 发布。

## 9. 实施阶段

### 阶段一：模板固化

目标：

- 后端固定专题 11 个板块。
- 后台只显示这 11 个专题板块。
- 前端继续兼容现有数据。

交付：

- 统一 `MODULE_SETS.topic`。
- 后台模板按钮改为 11 个。
- 覆盖度统计改为 11 个。

### 阶段二：资料类型模型

目标：

- 增加资料类型字段和模板配置。
- 后台可选择人物、活动、荣誉、成果、场景、视频、普通图文。

交付：

- 新增模板配置接口。
- 后台表单按类型切换字段。
- 资料预览使用对应抽屉模板。

### 阶段三：结构化数据表

目标：

- 新增 `content_items / content_item_assets / content_item_versions`。
- 新资料进入结构化表。
- 保持 `pages` 兼容。

交付：

- 数据库迁移。
- CRUD API。
- 审核流接入。

### 阶段四：前端结构化渲染

目标：

- 专题门户读取结构化资料。
- 抽屉按资料类型渲染。
- 卡片右侧统一单图轮播。

交付：

- 7 种抽屉模板。
- 自适应图片逻辑。
- 大屏扫码详情兼容结构化资料。

### 阶段五：旧数据迁移

目标：

- 将现有 blueprint JSON 和 pages 数据迁移为结构化资料。

交付：

- 迁移脚本。
- 迁移前备份。
- 迁移后质量检查。

## 10. 风险与控制

| 风险 | 控制方式 |
| --- | --- |
| 老师上传内容不规范 | 后台用固定字段和资料类型引导 |
| 图片数量不可控 | 前端统一单图轮播，不做宫格 |
| 文字过长 | 抽屉内部滚动，卡片只取摘要 |
| 旧数据无法一次迁移 | 保留 pages 和 blueprint JSON 兼容层 |
| 审核流程变复杂 | 沿用现有版本表思想，新增 content_item_versions |
| 前端模板过多难维护 | 固定 7 种资料类型模板 |

## 11. 推荐下一步

下一步建议先做“阶段一 + 阶段二”的设计落地：

1. 后端和后台固定专题 11 个板块。
2. 后台新增资料类型选择。
3. 先不大改数据库，用现有 `pages.body` 暂时承载结构化 JSON 或生成 HTML。
4. 前端抽屉先实现 7 种模板识别。
5. 等体验稳定后，再进入数据库结构化改造。

这样可以先验证后台录入体验和前端展示逻辑，再做较大的数据库迁移。
