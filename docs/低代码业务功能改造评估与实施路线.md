# 低代码业务功能改造评估与实施路线

## 1. 结论先行

当前项目适合做“低代码资料采集与业务表单能力”，不建议改造成完整的通用低代码平台。

推荐路线：

```text
保留现有前台展示效果
        ↓
后台增加资料采集模板
        ↓
老师按模板填写资料
        ↓
系统自动生成结构化资料
        ↓
复用现有审核、发布、专题展示、详情抽屉
```

这样既能满足“低代码快速开发业务功能”的要求，也能避免大改前端导致目前已经做好的展示效果被破坏。

一句话概括：

> 低代码只负责让后台资料更好填、更规范；前台继续使用现在已经确定的展示体系。

## 2. 为什么不建议做完整低代码平台

完整低代码平台通常包含：

- 页面自由拖拽。
- 自定义组件库。
- 自定义数据表。
- 自定义流程引擎。
- 自定义权限规则。
- 自定义前端布局。
- 自定义接口编排。

这些能力工程量很大，而且会带来两个明显问题：

1. 老师和普通管理员使用门槛会变高。
2. 前台页面风格容易失控，影响展厅大屏展示的统一性和美观度。

本项目的核心价值不是“让每个人都能搭页面”，而是“把学校、系部、专题资料标准化管理，并以统一视觉效果展示出来”。

所以第一阶段应当避开页面搭建器，先做后台业务表单和资料模板。

## 3. 推荐产品定位

建议后台模块命名为：

**资料采集模板**

不要直接叫“低代码平台”。

原因：

- 对学校用户更容易理解。
- 不会让使用者误以为可以随意改前台页面。
- 更贴近真实业务：收集资料、规范字段、自动展示。

后台可以这样组织：

```text
门户管理
专题管理
系部管理
资料采集模板
资料审核
素材管理
系统设置
```

## 4. 改造难度评估

整体难度：中等。

不是最难的前端重构，也不是简单加几个字段。真正需要谨慎的是数据库、审核流程和旧数据兼容。

| 模块 | 难度 | 风险 | 建议 |
|---|---:|---:|---|
| 后台动态表单 | 中 | 中 | 先做固定控件，不做复杂拖拽 |
| 数据库新增模板表 | 中 | 中 | 新增表，不破坏旧表 |
| 表单映射 content_items | 中 | 高 | 必须复用现有资料结构 |
| 前台展示适配 | 低 | 中 | 尽量不动现有展示，只补兼容 |
| 审核流程接入 | 中 | 中 | 沿用现有审核状态 |
| 权限和角色 | 中 | 中 | 第一阶段先区分管理员和老师 |
| 通用低代码页面搭建 | 高 | 高 | 第一阶段不做 |

综合判断：

- 如果做“资料采集模板”：可控，适合现在推进。
- 如果做“完整低代码平台”：风险偏高，容易拖慢项目并破坏现有成果。

## 5. 改造边界

### 5.1 第一阶段要做

- 固定专题 11 个板块。
- 固定 7 类资料类型。
- 后台支持按模板填写资料。
- 模板字段支持配置必填、提示、排序、默认值。
- 表单提交后自动生成 `content_items`。
- 图片、视频进入现有素材和资料附件体系。
- 提交后复用现有审核发布流程。
- 前台继续使用现有卡片、循环滚动和抽屉详情样式。

### 5.2 第一阶段不做

- 不做前台页面自由拖拽。
- 不做万能业务建表。
- 不做复杂流程设计器。
- 不做公式引擎。
- 不做自定义 CSS。
- 不允许老师改变前台卡片和抽屉排版。
- 不把现有页面全部推倒重来。

## 6. 固定业务模板

专题资料建议固定为 11 个板块：

| 顺序 | 板块 | key | 说明 |
|---:|---|---|---|
| 1 | 专题概况 | overview | 专题背景、建设目标、整体介绍 |
| 2 | 专业群布局 | majors | 专业设置、课程体系、就业方向 |
| 3 | 实训场景 | training | 实训基地、设备、教学场景 |
| 4 | 产教协同 | cooperation | 校企合作、订单班、共同体 |
| 5 | 名师名匠 | masters | 教学名师、技能大师、教师团队 |
| 6 | 优秀校友 | alumni | 校友人物、就业成果、成长故事 |
| 7 | 优秀学生 | students | 学生人物、竞赛经历、成长案例 |
| 8 | 专题成果 | achievements | 教学成果、项目成果、建设成果 |
| 9 | 技能大赛 | competitions | 赛事、获奖、承办活动 |
| 10 | 荣誉资质 | honors | 证书、奖项、资质认定 |
| 11 | 视频资源 | media | 宣传片、访谈、纪实视频 |

资料类型固定为 7 类：

| 类型 | key | 适合内容 |
|---|---|---|
| 普通图文 | article | 概况、介绍、说明类内容 |
| 人物 | person | 教师、校友、学生 |
| 活动 | activity | 比赛、合作、培训、交流 |
| 荣誉 | honor | 证书、奖项、认定 |
| 成果 | achievement | 项目成果、建设成果、案例 |
| 场景 | scene | 实训室、基地、教学空间 |
| 视频 | video | 视频资源和宣传片 |

## 7. 后台填写体验设计

老师端不应该看到复杂的低代码设计器，只需要看到清晰的资料填写表。

推荐流程：

```text
选择门户
  → 选择专题/系部
  → 选择板块
  → 选择资料模板
  → 填写文字
  → 上传图片/视频
  → 提交审核
```

管理员端可以多一些配置能力：

```text
选择内置模板
  → 调整字段
  → 设置必填项
  → 设置字段映射
  → 启用模板
```

为了降低操作难度，第一阶段模板字段不要太多。每个模板控制在 6 到 12 个核心字段比较合适。

## 8. 数据结构设计

现有 `content_items` 继续作为前台展示主数据源。

低代码只新增一层“填写记录”和“模板定义”。

### 8.1 模板表

表名：`lowcode_forms`

用途：保存资料采集模板基础信息。

建议字段：

- `id`
- `name`
- `code`
- `description`
- `target_content_type`
- `target_module_key`
- `enabled`
- `created_by`
- `created_at`
- `updated_at`

### 8.2 模板版本表

表名：`lowcode_form_versions`

用途：保存字段配置，方便后续模板升级和回滚。

建议字段：

- `id`
- `form_id`
- `version_no`
- `schema_json`
- `status`
- `created_by`
- `created_at`

`schema_json` 示例：

```json
{
  "fields": [
    {
      "key": "title",
      "label": "标题",
      "type": "text",
      "required": true,
      "mapping": "content_item.title"
    },
    {
      "key": "summary",
      "label": "摘要",
      "type": "textarea",
      "required": false,
      "mapping": "content_item.summary"
    },
    {
      "key": "gallery",
      "label": "展示图片",
      "type": "image_upload",
      "required": false,
      "mapping": "content_item.assets.gallery"
    }
  ]
}
```

### 8.3 填写记录表

表名：`lowcode_records`

用途：保存老师填写的原始资料，并关联生成后的结构化资料。

建议字段：

- `id`
- `form_id`
- `form_version_id`
- `project_id`
- `content_item_id`
- `status`
- `data_json`
- `submitted_by`
- `submitted_at`
- `reviewed_by`
- `reviewed_at`
- `review_note`
- `created_at`
- `updated_at`

### 8.4 填写记录素材表

表名：`lowcode_record_assets`

用途：保存表单上传素材和字段角色的关系。

建议字段：

- `id`
- `record_id`
- `asset_id`
- `role`
- `title`
- `caption`
- `sort_order`
- `created_at`

## 9. 数据映射方式

低代码表单提交后，不直接给前台用，而是转换为 `content_items`。

| 模板字段 | 映射目标 |
|---|---|
| 标题 | `content_items.title` |
| 副标题 | `content_items.subtitle` |
| 摘要 | `content_items.summary` |
| 正文 | `content_items.body_json` |
| 类型扩展字段 | `content_items.meta_json` |
| 所属板块 | `content_items.module_key` |
| 资料类型 | `content_items.content_type` |
| 封面图 | `content_item_assets.role = cover` |
| 人物照 | `content_item_assets.role = portrait` |
| 证书图 | `content_item_assets.role = certificate` |
| 图集 | `content_item_assets.role = gallery` |
| 视频 | `content_item_assets.role = video` |

这样前台不用理解低代码表单，只读取熟悉的结构化资料。

## 10. 与现有前台的关系

前台展示尽量不变。

保持：

- 学校门户页面结构。
- 系部门户页面结构。
- 专题页 11 个板块。
- 顶部栏统一样式。
- 卡片循环滚动。
- 详情抽屉。
- 图片原比例缩放和轮播。
- `/display?project=...&code=...` 详情访问方式。

低代码改造只改变资料从哪里来，不改变资料怎么展示。

## 11. 分阶段实施路线

### 阶段一：模板固化

目标：先把后台资料录入入口整理清楚。

交付内容：

- 固定 11 个专题板块。
- 固定 7 类资料类型。
- 后台显示“资料采集模板”入口。
- 内置常用模板。
- 保留原有资料编辑入口作为高级编辑。

风险：低。

### 阶段二：动态表单

目标：老师可以按模板填写资料。

交付内容：

- 新增低代码模板表。
- 新增模板字段 JSON。
- 后台根据模板动态渲染表单。
- 表单记录保存到 `lowcode_records`。

风险：中。

### 阶段三：自动生成结构化资料

目标：表单提交后自动进入现有展示体系。

交付内容：

- 将 `lowcode_records` 映射为 `content_items`。
- 上传图片自动绑定 `content_item_assets`。
- 接入现有审核发布流程。
- 前台无需大改即可展示。

风险：中。

### 阶段四：模板版本和复制

目标：管理员可以长期维护模板。

交付内容：

- 模板复制。
- 模板启用/停用。
- 模板版本记录。
- 已提交记录保留当时模板版本。

风险：中。

### 阶段五：体验增强

目标：让资料录入更省事。

交付内容：

- 图片批量上传。
- 图片排序。
- 字段分组。
- 表单预览。
- 从已有资料复制生成新资料。
- 后续可接入 AI 摘要和文案润色。

风险：低到中。

## 12. 最小可行版本

如果要稳妥推进，第一版建议只做这些：

- 后台新增“资料采集模板”入口。
- 内置 11 个板块模板。
- 每个模板包含固定字段。
- 表单提交后生成 `content_items`。
- 保留旧资料编辑方式。
- 前台展示完全不改。

第一版不做：

- 字段拖拽。
- 页面搭建。
- 自定义流程。
- 复杂权限。
- 跨业务系统集成。

这样可以最快验证价值，同时把风险压到最低。

## 13. 对当前项目的推荐实施顺序

建议按下面顺序改：

1. 先梳理并固定后台模块名称和入口。
2. 新增低代码相关数据库表。
3. 写入 11 个内置模板。
4. 增加模板列表 API。
5. 增加按模板提交资料 API。
6. 后台增加动态表单弹窗。
7. 提交后生成现有 `content_items`。
8. 用现有专题页验证展示效果。
9. 同步最新数据库快照。
10. 再考虑模板复制、版本、字段拖拽。

## 14. 风险控制清单

开发时需要坚持以下原则：

- 不删除现有 `content_items`。
- 不删除现有 `pages` 兼容逻辑。
- 不改动前台核心视觉布局。
- 不把模板字段直接暴露为前台 CSS。
- 不让老师配置页面布局。
- 每次数据库迁移前备份 `expo.db`。
- 大素材继续留在 `uploads/`，不要提交仓库。
- 每次提交 GitHub 前同步 `database/expo-latest.db`。

## 15. 最终建议

当前项目应该做的是：

**业务表单低代码化，前台展示模板固定化，资料数据结构化。**

这条路线的优点是：

- 改造难度可控。
- 不会推翻现有成果。
- 后台会更符合学校资料管理逻辑。
- 老师上传资料会更规范。
- 前台展示仍然统一、美观、稳定。
- 后续可以继续扩展成更完整的业务表单平台。

推荐先实施“资料采集模板”的最小版本。等它稳定后，再逐步增加字段拖拽、模板复制、版本管理和更多业务表单能力。
